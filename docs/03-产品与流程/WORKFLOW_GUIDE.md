# 核心工作流指南

- 最后核对日期：2026-05-17
- 核对口径：仅以已提交代码中的稳定实现为准，不纳入当前工作区未提交改动
- 核对范围：`frontend/src/App.tsx`、`frontend/src/auth/permissions.ts`、`frontend/src/components/`、`backend/app/routers/`、`backend/app/platform/`

## 1. 目标

本文件用于概括当前 MDAMS 原型已经落地的核心业务工作流，帮助读者快速理解系统不是“单页面上传工具”，而是由多条关联链路组成。

## 2. 总体流程图

当前项目可以粗分为七条核心链路：

1. 登录与角色识别
2. 二维资产上传与查看
3. 图像记录拆分工作流
4. 三维资源管理与平台聚合
5. 视频资源浏览与平台接入
6. 统一平台浏览、筛选与跳转
7. 申请、审批与交付

此外，Mirador AI 辅助链路作为二维 IIIF 查看体验的增强能力存在。

## 3. 登录与角色识别

当前登录流程：

1. 前端读取 `/api/auth/users` 获取可用测试用户
2. 用户提交用户名和密码到 `/api/auth/login`
3. 后端返回 token 与当前用户上下文
4. 前端保存 token，并继续读取 `/api/auth/context`
5. 前端按权限裁剪菜单与页面入口

当前角色识别不仅影响“能不能看到菜单”，还影响：

- 能否读取资产列表
- 能否进入图像记录工作台
- 能否进入申请管理
- 能否看到责任范围内资源
- `resource_user` 作为单角色用户时，前端会覆盖菜单，仅显示统一资源目录与申请车

## 4. 二维资产主链路

当前二维资产主链路如下：

1. 具备 `image.upload` 的用户上传文件
2. 后端创建资产记录并写入挂载目录
3. 后端生成元数据层与基础状态
4. 需要衍生文件时进入 IIIF access 处理
5. 资产在列表页、详情页、统一平台和 Mirador 中可查看

当前这条链路覆盖：

- 上传
- 列表
- 详情
- 预览图
- Manifest
- Mirador
- 下载
- BagIt 导出

## 5. 图像记录拆分工作流

当前图像记录工作流是项目的一条重要新链路。

### 5.1 元数据录入人员

`image_metadata_entry` 负责：

- 创建图像记录
- 编辑结构化信息
- 提交图像记录
- 退回后继续修订

### 5.2 摄影上传人员

`image_photographer_upload` 负责：

- 查看待上传记录池
- 上传文件
- 与指定记录匹配
- 触发上传后的校验流程

### 5.3 当前意义

这条链路意味着当前系统已经从“先传文件再补说明”演进为“记录和文件可以分离协作”。

## 6. 统一平台链路

统一平台当前是聚合入口，而不是新的独立资源来源。

当前流程：

1. 用户进入统一资源目录
2. 前端请求 `/api/platform/sources` 和 `/api/platform/resources`
3. 平台层从已注册来源适配器聚合资源
4. 前端按二维 / 三维 / 视频标签页注入 `source_system`
5. 用户通过关键词、状态、类型、profile、预览状态等条件筛选资源
6. 从目录跳转到统一详情或来源详情

当前统一平台主要用于：

- 跨来源浏览
- 统一筛选
- 统一资源详情跳转
- 统一资源加入申请车
- 根据资源类型分流预览：二维打开 Mirador，三维和视频进入统一详情中的专门预览

## 7. 三维资源链路

当前三维相关流程如下：

1. 具备 `three_d.view` 或更高权限的用户进入三维管理
2. 三维操作人员上传单文件或多文件资源包
3. 后端保存对象、版本和文件角色信息
4. 前端展示三维详情和查看摘要
5. 统一平台按三维数字对象粒度聚合三维来源
6. 用户可从统一平台进入对象级详情，并查看默认可预览表现

当前三维链路已经具备：

- 对象与版本概念
- 多文件角色区分
- Web 查看入口
- 平台聚合接入
- 对象级统一平台摘要

## 8. 视频资源链路

当前视频资源是统一平台的多模态来源之一。

当前视频相关流程如下：

1. 后端启动时注册视频路由与视频来源适配器
2. 视频样例资源通过 seed 逻辑进入系统
3. 统一平台按 `video` 来源聚合视频资源
4. 用户在统一目录的视频标签页浏览资源
5. 用户进入统一详情后在线播放或下载视频资源

当前视频链路主要用于验证统一平台多模态扩展，不等同于完整视频生产管理工作流。

## 9. 申请、审批与交付链路

当前申请相关流程如下：

1. `resource_user` 浏览资源
2. 用户把目标资源加入申请车
3. 前端提交申请单到 `/api/applications`
4. `application_reviewer` 进入申请管理页面
5. 审批通过或拒绝
6. 审批通过后可导出交付包

这条链路当前已经形成了从浏览到导出的最小闭环。

申请条目当前可来自二维、三维或视频等统一平台资源。前端会根据来源系统选择交付格式，例如二维为 `image`、三维为 `3d_package`、视频为 `video`。

## 10. AI / Mirador 辅助链路

当前 AI / Mirador 链路服务二维 IIIF 查看体验：

1. 用户在 Mirador 查看器中打开二维资源
2. 前端 AI 面板向 `/api/ai/mirador/interpret` 提交当前上下文和自然语言指令
3. 后端返回查看器动作计划和工具调用兼容结构
4. 前端执行缩放、平移、检索、对比等已支持动作

这条链路当前应理解为演示性辅助控制能力，而不是完整自动化代理系统。

## 11. 当前工作流与菜单的关系

前端菜单与工作流的对应关系大致如下：

| 菜单 | 对应工作流 |
| :--- | :--- |
| 总览 | 登录后总览 |
| 二维资源 | 二维资产浏览与详情 |
| 申请车 | 申请提交 |
| 入库处理 | 二维上传与入库操作 |
| 统一资源目录 | 平台聚合浏览 |
| 统一资源详情 | 平台目录内部详情状态，不是左侧直接菜单 |
| 三维管理 | 三维对象与版本 |
| 申请管理 | 审批与导出 |
| 影像信息录入 | 元数据录入与摄影上传协作 |

## 12. 当前边界

当前工作流虽然已成型，但仍有这些边界：

- 平台统一检索仍以适配器内筛选为主，还不是独立全文检索系统
- 图像记录与正式入库的状态治理还可继续增强
- IIIF 访问控制还需要继续收口
- 三维治理与兼容性仍需完善
- 视频链路是多模态平台来源示例，还不是完整视频子系统
- AI / Mirador 链路可演示，但任务编排、审计和权限细化仍需继续增强
- 申请流的更细粒度规则仍可继续细化
